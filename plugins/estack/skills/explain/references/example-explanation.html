How estack reaches two agents

One repository, two coding tools that share almost none of their plugin machinery, and the small pile of scripts that hides the difference.

Overview

estack is a personal scaffold that pushes the same working habits into two different coding agents. Claude Code and Codex both support plugins, both read instruction files, and the resemblance stops roughly there. Their manifests use different schemas, their install commands differ, one caches a snapshot while the other tracks a marketplace, and only one of them runs hooks that estack cares about.

The repository handles this with three delivery channels rather than one.

The source separates shared content from host-only content. skills/ holds shared skills, skills-claude/ and skills-codex/ hold host-only skills, and claude/ holds Claude-only hooks. The build script combines the right source for each host:

.generated/claude/estack    shared + Claude-only
.generated/codex/estack     shared + Codex-only

Both tools install a plugin named estack. Package composition keeps Claude-only hooks and skills out of Codex, and keeps Codex-only skills out of Claude Code.

Why it matters

A skill placed in the wrong plugin either fails to reach Codex at all, or reaches it carrying instructions about tools Codex does not have. The directory you create a skill in is a distribution decision, not just filing.

Data flow: what happens when you edit a skill

Say you fix a sentence in plugins/estack/skills/review/SKILL.md. Nothing has reached either agent yet. Both tools read from their own installed copy, not from your clone. Running scripts/refresh.sh walks three paths in sequence, and the same edit becomes visible at three different moments.

your editreview/SKILL.mdline 12, one sentence changed, committed as a1b2c3d
./scripts/refresh.sh
Codex, step 1plugin remove, then addestack@estack reinstalled from the marketplace. Visible after Force Reload Skills, inside the running session.
step 2home instructions~/.codex/AGENTS.override.md rewritten. ~/CLAUDE.local.md already pointed at the clone, so nothing to copy.
Claude Code, step 3uninstall, then installCache refreshed. Still invisible until you restart the app.

Read that middle box twice. The Claude Code home instructions needed no step at all, because a symlink has nothing to copy, while the Claude Code skill needed the slowest path of the three. Same tool, same refresh, opposite behavior, and the reason is the next three sections.

Codex, through the marketplace

refresh.sh first checks whether Codex is really usable, and it does not trust command -v alone:

if command -v codex >/dev/null 2>&1 && codex --version >/dev/null 2>&1; then
  "$REPO_DIR/scripts/install-codex.sh"
else
  echo "Codex: 'codex' CLI missing or not runnable; skipped." >&2
fi

A stale launcher shim pointing at a moved application bundle still sits on PATH, so command -v succeeds and the invocation fails. Probing with a cheap --version lets the Claude Code half of the refresh continue instead of dying on someone else's broken install.

Inside install-codex.sh, the plugin is removed before it is added. That looks redundant and is not: Codex keeps hook state for a plugin in ~/.codex/config.toml, and a plain re-add can leave a hook active that no longer exists in the source. There is even a dedicated function that deletes the obsolete Fable hook's TOML section by matching its header line and skipping to the next [.

Home instructions, two mechanisms for one file

This is the sharpest asymmetry in the repository, and install-home-instructions.sh exists entirely because of it.

Claude CodeCodex
Reads~/CLAUDE.md, then appends ~/CLAUDE.local.mdAGENTS.md walk from the repo root, never your home ~/CLAUDE.md
OverrideThe .local file is an append, so estack can take that slot outrightAGENTS.override.md replaces the base file at its level
estack installsA live symlink into the cloneA generated file: your home instructions concatenated with estack's
Edit visibilityImmediate, next sessionStale until the script runs again

Because Codex has no append mechanism, estack cannot simply add itself. It has to rebuild the whole override, which means copying your personal instructions in alongside its own. That generated file needs a guard so it never silently eats a hand-written override:

if [ -e "$OVERRIDE" ] && ! grep -qF "$MANAGED_MARKER" "$OVERRIDE" 2>/dev/null; then
  echo "codex: $OVERRIDE exists and is not estack-managed; leaving it alone"
else
  ...regenerate...
fi
Subtle

Detection matches $MANAGED_MARKER as a substring, not the full header line. The surrounding wording can change without orphaning files generated by an older version of the script. That is what makes the header safe to edit.

Claude Code, last and coarsest

Claude Code installs estack as a cached snapshot, so the script uninstalls both plugins, updates the marketplace, and reinstalls. Even then the change is not live: Claude Code loads plugins at startup, and claude plugin install only refreshes the cache. You have to restart. Codex, by contrast, offers Force Reload Skills inside a running session.

So the same edit becomes visible at three different moments. Home instructions on the Claude side apply next session with no install step at all, because the symlink means there is nothing to copy. Codex skills apply after a reload. Claude Code skills apply after a full restart.

Decision audit

These are the choices where a reasonable alternative would have produced a different system. The reasoning is inferred from the code and its comments, not from the author.

Two plugins rather than one plugin with conditional content

Choice
Fable-only material lives in a separate plugin that the Codex manifest omits.
Evidence
The two marketplace manifests list different plugin sets. CLAUDE.md states the rule explicitly.
Alternative
One plugin whose skills say "ignore this in Codex". Cheaper to maintain, but every Codex session would then carry descriptions for tools it cannot use, and skill descriptions load whether or not the skill runs.
Limit
The split is by tool, not by model. A Fable session in Codex, if that ever exists, gets nothing.
Reviewer question
What happens the first time a skill is genuinely useful to both tools but only mechanically possible in one?

A live symlink for Claude, a generated copy for Codex

Choice
~/CLAUDE.local.md links into the clone. ~/.codex/AGENTS.override.md is regenerated from source.
Evidence
The header comment in install-home-instructions.sh derives both from what each tool supports.
Assumption
That ~/CLAUDE.md can be treated as opaque rendered text whatever produced it, which is what keeps the script Nix-agnostic on a machine where that file is generated by Home Manager.
Cost
The two sides drift between refreshes. Editing home/estack-instructions.md changes Claude's behavior immediately and Codex's not at all until the script runs.
Reviewer question
Is that drift ever going to produce a confusing session where the two agents disagree about their own instructions?

The Fable hook only fires on resume and compact

Choice
The SessionStart matcher is resume|compact. Fresh sessions are covered by the always-loaded home instructions instead.
Constraint
The hook payload carries no model field, so the script recovers the model by reading the transcript for the last non-sidechain assistant message. At startup there is no transcript to read.
Consequence
Every session on every model loads the Fable guidance, then ignores it unless it is Fable or Mythos. That is the price of not being able to detect the model early.
Reviewer question
Is shortening that text the only available lever, or is there a startup-time signal nobody has looked for yet?

Explore

The claim worth testing is the one from the decision audit: that the Claude side is live and the Codex side is a snapshot. Three commands show it, and none of them write anything.

Run these from anywhere. Nothing here modifies the repository.

Start with what each tool actually has on disk:

ls -l ~/CLAUDE.local.md ~/.codex/AGENTS.override.md

The first is a symlink, shown with an arrow pointing into your estack clone. The second is an ordinary file whose modification time is the last time you ran the installer. If it does not exist yet, that is its own answer: the script has never run here, and the Claude side has been working anyway.

Predict before running the next command. Both files are supposed to deliver the same instructions. How many lines does each one contain?

wc -l ~/CLAUDE.local.md ~/.codex/AGENTS.override.md

The answer is lopsided, and the reason is the interesting part. Look at the small one:

cat ~/CLAUDE.local.md

Five lines: a heading and two import directives, each just @ followed by a filename. Claude Code resolves those imports when it loads the file, so the prose never sits on disk at that path and an edit in the clone takes effect with no install step. The Codex file cannot work that way, because AGENTS.override.md replaces rather than appends, so the installer flattens everything into one literal copy. Check its modification date against your last edit to the clone and you are looking straight at the drift.

What this demonstrates

The two channels are not the same mechanism with different paths. One is a pointer chain that stays live. The other is a build artifact that goes stale the moment you edit the source. That is the drift named in the decision audit, visible in three commands.

For the plugin side, compare what each tool believes it has installed:

claude plugin list
codex plugin list

Both tools should report one plugin: estack@estack. The installed contents differ by host because refresh.sh builds each package before installation.

Quiz

Five questions. Click an answer for feedback.

1. You add a skill to plugins/estack/skills-claude/. A colleague running Codex reports they cannot see it. What happened?

Answer: B. The Codex package combines shared and Codex-only skills. No amount of reloading will surface a Claude-only skill. The fix is to decide whether the skill belongs in the shared source instead.

2. Why does refresh.sh run codex --version when command -v codex has already succeeded?

Answer: C. A shim pointing at a moved app bundle is still on PATH. Without the probe, a broken Codex install would abort the script under set -e and the Claude Code refresh below would never run.

3. You change the wording of the header line that install-home-instructions.sh writes into the generated override. What breaks on a machine that installed the previous version?

Answer: A. The guard is grep -qF "$MANAGED_MARKER" against the marker alone, not the full line. Had it matched the whole header, every existing install would have been orphaned as unmanaged.

4. Why does the Fable hook not fire on a fresh session start?

Answer: C. Detection works by reading the last non-sidechain assistant message in the transcript, which only exists on resume or compact. Startup coverage falls back to the always-loaded home instructions, which is why every model pays for that text.

5. You edit a skill, commit, and run refresh.sh. Your open Claude Code session still uses the old skill. Why?

Answer: B. claude plugin install refreshes the cached snapshot but does not reload a running process. Codex differs here: Force Reload Skills works inside a live session. Whether an unpushed commit matters depends on how your marketplace was added: a local one installs straight from the clone, while one added from GitHub gets refreshed by marketplace update against origin.
